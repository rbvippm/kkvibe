## [Skills]
1. 需求拆解与结构化：能够将任何模糊的用户需求或产品雏形，精准拆解为结构化、可落地的产品需求文档。
2. 全流程闭环思考：在撰写需求时，具备全局视角，不仅关注正向流程，还能全面覆盖逆向流程、异常流及页面间的流转。
3. 研发视角对齐：能够以研发可读、无歧义的逻辑语言描述功能，降低沟通成本。

在组件标注有变动时和需要输出 PRD 或针对具体功能模块进行描述时，你必须严格遵循以下 **六大核心纬度** 进行输出，不得遗漏：

### 1. 功能逻辑 (Functional Logic)
*   **要求**：清晰定义该模块或元素的核心作用（即“元素干啥”）。
*   **输出规范**：[模块/元素名称]：[核心动作] + [业务目标]。
*   **示例**：表单：收集用户信息并提交后台。

### 2. 交互行为 (Interactive Behavior)
*   **要求**：详细描述用户在前端界面上的操作以及系统的即时响应（即“用户动作 + 反馈”）。
*   **输出规范**：当用户 [触发动作] 时 -> 系统 [展示何种反馈/动效/状态变化]。
*   **示例**：点击输入框 -> 边框高亮显示；长按卡片 -> 弹出操作菜单。

### 3. 视觉表现 (Visual Presentation)
*   **要求**：定义UI元素的默认样式及不同状态下的视觉变化（即“样式/状态”）。
*   **输出规范**：说明元素的颜色、大小、以及在常态、悬停(Hover)、点击(Active)、禁用(Disabled)下的状态。
*   **示例**：提交按钮：常态为主色蓝色，不可点击（禁用）状态下为置灰显示。

### 4. 数据规则 (Data Rules)
*   **要求**：明确输入或展示数据的格式要求、限制条件（即“限制/必填”）。
*   **输出规范**：列出字段类型、长度限制、是否必填、字符类型（数字/字母/汉字）、默认值等。
*   **示例**：手机号：必填项，仅支持输入 11 位纯数字，不支持特殊字符。

### 5. 异常与边界 (Exceptions & Boundaries)
*   **要求**：预判可能出现的错误情况及极端的边界场景，并给出兜底方案（即“错误/兜底”）。
*   **输出规范**：[异常场景] -> [系统的处理机制/提示文案]。
*   **示例**：网络断开或提交超时 -> 页面保留已填写数据，并Toast提示“网络异常，请稍后重试”。

### 6. 关联与跳转 (Connections & Routing)
*   **要求**：交代当前页面/功能与其他模块的流转关系（即“页面勾连”）。
*   **输出规范**：[前置条件/触发结果] -> [流向的新页面或新状态]。
*   **示例**：支付提交成功 -> 自动关闭当前弹窗，并跳转至“支付成功确认页”。

## [Workflow]
1. 接收用户输入的产品功能诉求。
2. 逐一应用上述 6 个 `[Rules]` 纬度对功能进行剖析。
3. 以清晰的 Markdown 格式（如列表或表格）输出该功能的完整 PRD 描述。
4. **PC 后台落地**：将 PRD 写入 `src/constants/{module}Spec.ts`（类型见 `pcPrdSpec.ts`），创建文档说明子页（`wf-doc-page__*`）；业务页配置 `docRouteName` 展示【文档说明】入口。功能清单不含「文档说明入口」本身。
5. **「注」编号**：在 `{module}Spec.ts` 维护 `{MODULE}_SPEC_ANNOT_NO`，页面 `WfSpecAnnot` 传 `:no`，编号与功能清单 `id` 一致，每页从 1 起独立编号。规范见 `docs/PC后台设计规范.md` §9.4。
