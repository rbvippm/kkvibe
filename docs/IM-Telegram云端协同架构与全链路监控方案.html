IM 云端协同架构改造与全链路监控方案

当前 App、H5、PC 均可独立登录，但三端各自维护本地会话与消息状态，导致历史记录、未读数和会话排序无法一致。方案将系统重构为“云端状态机是唯一真相”，在保留独立登录的同时实现三端实时同步，并解决 App 掉签重装后的数据丢失。

Telegram 式云端协同会话与历史消息漫游PTS 增量同步多端未读一致端到端可观测
云端 SSOT本地 SQLite 降级为可重建缓存
1–2 秒目标为恢复首屏，不是下载全部历史
≥ 99.9%消息端到端到达率目标
分阶段灰度服务端双写 → 多端接入 → 全量切换
01

方案结论与改造边界

不是给本地数据库做备份，而是重新定义消息系统的数据所有权。

架构结论

云端成为唯一真相

消息、会话、未读、已读位点、撤回与删除状态均由服务端持久化；客户端缓存可随时清空重建。

产品结论

三端共享同一账号状态

保留 App、H5、PC 现有独立登录能力，将会话、历史、未读、置顶和删除状态统一改为云端同步。

运营结论

掉签只影响安装，不再摧毁数据

重新安装并登录后先恢复会话首屏、未读和近期消息，久远历史按需从云端加载。

关键口径：“1–2 秒恢复”指网络正常时恢复会话首屏与近期消息窗口；完整历史记录保持云端可访问，不应承诺在 1–2 秒内把全部历史下载到本机。
命名说明：本文“WhatsApp 模式”指当前系统的端侧中心实现，“Telegram 模式”指目标云端协同范式，并非对两款产品当前全部技术实现的精确复刻。
02

现状剖析与结构性痛点

掉签只是触发器，真正问题是本地数据库承担了不可恢复的唯一数据源角色。

当前架构

三端存在多个本地真相

  • App、H5、PC 已能分别独立登录。
  • 服务器主要承担消息路由与短期中转。
  • 会话、历史、未读高度依赖各端本地存储。
  • 同一账号在三端形成相互割裂的状态副本。
核心矛盾

缺少云端统一真相，三端必然分叉

App、H5、PC 当前均可独立登录，并不是以 App 作为唯一载体；但同一账号的会话与历史记录分别由各端本地维护。服务端/云端没有统一状态与同步游标时，一端产生的变化无法可靠同步到另外两端，三端数据必然逐渐不一致。

同时，iOS 掉签、重签或重装会导致新沙盒与旧数据库物理隔离；如果云端还没有持久化备份完整历史，App 端就不存在恢复来源。只要云端记录完整，各端重新登录后都可以重建一致的本地数据。

灾难链路

分发受限依赖超级签 / 企业证书
高频掉签证书吊销、App 无法打开
沙盒归零重装生成新沙盒 UUID
状态割裂App/H5/PC 会话与未读各自维护
结果不可恢复App 重装后空白，三端数据继续不一致
根因判断：证书治理只能降低掉签概率，无法从根本上保证数据安全。只要本地仍是唯一数据源，换机、清缓存、磁盘损坏同样会触发相同事故。

端侧中心与云端协同模式对比

核心变化不是 UI，而是 SSOT、多端身份和消息持久化责任迁移。

维度当前端侧中心模式目标云端协同模式业务收益
数据源真相App/H5/PC 各自以本地数据库为事实来源云端消息与状态数据库；客户端只负责交互和缓存消除三端数据分叉，掉签、换包、换机不再导致永久丢失
多端关系三端均可独立登录，但会话、历史、未读分别维护三端保持独立登录，并共同订阅同一份云端账号状态任一端产生消息或已读操作，其他端即时对齐
认证登录各端已有独立鉴权，但登录后的数据恢复与设备状态未统一复用现有鉴权，补充统一设备会话、同步游标和云端恢复不重做登录体系，重点解决登录后的状态一致性

安全决策：云端同步并不天然要求服务器持有明文，但跨端检索、审核、密钥恢复和 E2EE 会显著增加复杂度。本期必须由产品、安全与合规共同确认普通云聊、秘密会话或分级会话策略。

写路径

先持久化，再确认

网关收到消息后进入可靠写入链路，数据库与事件日志成功后才返回 MsgAck，避免“已显示成功但云端未落盘”。

读路径

缓存优先，云端补齐

本地命中则秒开；本地为空显示骨架屏并拉取云端窗口，结果回填缓存。

恢复路径

快照 + 增量

先返回会话快照和活跃消息窗口，再按 PTS 顺序追平，避免从 0 重放全部历史事件。

存储校准：Redis 适合作缓存、幂等键和短期队列，不建议作为消息持久化主链路；高可靠事件流优先 Kafka/Pulsar。ClickHouse 更适合日志与分析，冷历史建议使用归档数据库或 S3 分块对象并保留可检索索引。

06

消息历史、主键与媒体云解耦

服务端序列保证排序，random_id 保证发送幂等，msg_id 保证跨端引用稳定。

标识体系

random_id + msg_id + seq

random_id用于客户端重试去重；msg_id用于业务引用；msg_seq_id用于会话内确定排序。

单向删除

用户可见性 Tombstone

按用户记录不可见范围或删除位点，并定期压缩，避免逐消息标记无限膨胀。

双向撤回

服务端状态更新

消息标记已撤回并生成更新事件；全部终端替换正文、索引和会话摘要。

双向删除

不限制时间，双方同步删除

不校验消息发送时间，用户可对任意历史消息执行双向删除。服务端将消息对会话双方标记为不可见，并向双方全部在线终端广播删除事件；底层数据是否保留按审计与合规策略处理。

双向分页与定位跳转

GET /messages/history?peer_id=1001&offset_id=5000&limit=30&direction=older
GET /messages/context?peer_id=1001&focus_msg_id=5001&before=20&after=20

历史加载采用稳定游标，不使用客户端时间排序。点击搜索结果、回复引用或置顶消息时，服务端返回目标消息及前后上下文，客户端直接建立窗口。

07

本地缓存与 PTS 同步引擎

实时链路可能丢包，差异同步必须能够独立恢复全部权威状态。

同步状态机

客户端 local_pts = 100        服务端 server_pts = 120

正常在线：Update(pts=101, pts_count=1) → 事务应用 → local_pts=101
发生空洞：new_pts != local_pts + pts_count → 暂停推进 → getDifference
重装登录：local_pts=0 → 拉取 snapshot + active windows → 保存 snapshot_pts
断网恢复：getDifference(local_pts) → 顺序应用 updates → 提交最新 pts
PTS 校准：批量事件不能只判断 new_pts = current_pts + 1，更新包应携带 pts_count，校验 new_pts = current_pts + pts_count；快照与增量必须有一致的切点，防止快照期间漏消息。

同步接口

POST /sync/getDifference
{ "pts": 100, "limit": 100, "device_id": "..." }

→ updates[]
→ next_pts
→ has_more
→ too_long: false

若差异超过服务端窗口：too_long=true，返回 snapshot_token，客户端执行快照重建。
读流程

Read-through Cache

先读 SQLite 最近窗口；未命中时展示骨架屏，从云端拉取后以事务写回。

写流程

乐观更新 + 正式确认

先以 random_id 显示“发送中”；MsgAck 返回 msg_id/seq/pts 后替换并确定排序。

淘汰流程

LRU + 可恢复

本地设置约 500MB 或近 30 天缓存上限；淘汰不删除云端记录，翻看时重新拉取。

冲突与幂等规则

  • 所有更新以账号 PTS 顺序、单个数据库事务应用；失败不得推进游标。
  • 服务端以 sender_id + peer_id + random_id 建立幂等键并持久化唯一约束，Redis 只做加速。
  • 已读位点、置顶顺序采用版本号或 CAS，禁止旧设备覆盖较新状态。
  • 客户端重建时先关闭实时消费，建立快照后从 snapshot_pts 接续增量，再恢复推送。

实施演进方案

先构建可恢复的服务端事实，再接入客户端，最后完善性能与可观测性。

阶段主要交付退出条件
阶段 0 · 数据盘点与双写设计现网消息生命周期、用户规模、历史量、合规保存期、迁移与回滚方案容量模型、字段字典、数据口径和灰度边界确认
阶段 1 · 存储与状态机消息永久存储、User_Dialog、PTS 日志、dialogs/history/difference API、现有多端鉴权接入统一设备会话服务端可从空客户端恢复完整账号状态

10

五类高频异常监控与自愈

监控不是只告警，每个高频故障都应有端侧或服务端自动修复动作。

10.1 丢消息：上行失败与下行 PTS 空洞

场景示例：两条连续消息中间少了一条

用户 A 连续发送“会议改到 3 点”和“收到请回复”。用户 B 先收到序列 5001，下一条却直接变成 5003，页面上只显示“收到请回复”，关键的时间变更消失。客户端发现 5002 缺失后，不继续推进 PTS，立即从云端补拉 5002，再按正确顺序展示两条消息。

检测
  • 更新包校验 new_pts = current_pts + pts_count。
  • 出现 Gap 时暂停推进并调用 /sync/getDifference。
  • 发送 5 秒未收到 MsgAck，进入可控重试队列。
自愈
  • 小空洞增量补齐，大空洞执行快照重建。
  • 重试沿用 random_id，避免补偿产生重复消息。
  • 写入失败明确返回失败，不展示永久“已发送”。
指标窗口/维度阈值响应
E2E Delivery Rate5 分钟滑动窗口< 99.9%P1；检查事件队列积压与路由
PTS Gap Frequency端/版本/分群环比突增 > 20%P2；检查推送丢包和发布缺口
Send Failure Rate地域/网络> 0.5%P2；检查长连接入与写入链路

10.2 消息重复：客户端与服务端双重幂等

客户端发送携带 random_id；服务端 Redis SetNX 可做快速拦截，但数据库必须有持久唯一约束。SQLite 对 msg_id 建唯一索引，重复推送只更新状态、不重复渲染。

场景示例：进电梯时一条消息被重试三次

用户点击一次“我已经到了”，网络随即断开，客户端因未收到 ACK 自动重试三次。如果每次都当作新消息，接收方会看到三条相同内容。正确处理是三次请求沿用同一个 random_id，服务端只生成一个 msg_id；后续重试只返回原确认结果，接收方始终只看到一条。

Server Deduplication Rate

正常约 0.1%–0.5%；若 > 2%，排查弱网重试风暴、ACK 丢失和客户端超时设置。

Client Duplicate Dropped

区分实时推送与 difference 重叠，用于优化同步窗口，但不能通过关闭幂等来“消灭指标”。

10.3 消息乱序：服务端序列为唯一排序基准

废弃客户端时间排序，按会话内 msg_seq_id 渲染。并发写入需由单会话分区、队列顺序或等价机制保证；客户端发现倒挂上报 im_render_out_of_order 并插入有序缓冲区。

场景示例：“更正消息”显示在原消息之前

用户先发“集合地点在一楼”，随后马上发“更正：改到二楼”。两次请求被不同节点处理，第二条更快到达接收端；如果按到达时间直接追加，用户会先看到“改到二楼”，随后又看到“一楼”，容易误判最终地点。服务端为两条消息分配连续 seq，客户端按 seq 重排后始终保持原始发送顺序。

目标：乱序渲染率应为 0。任何持续大于 0 的服务端序列倒挂均按 P1 处理；客户端因历史分页插入产生的位置变化需单独统计，避免误报。

10.4 未读错乱：服务端 Read Pointer 为绝对真相

已读位点在账号维度单调推进，所有设备接收更新。若采用 unread = max_seq - read_inbox_max_seq，必须确保序列只统计该用户应计未读的收件消息；包含本人消息、系统消息、删除消息时应使用物化计数或可见收件序列。

场景示例：同一会话在三端显示不同数字

账号在 App 打开会话并读完消息后，App 红点已经消失，但 H5 仍显示 3 条、PC 显示 1 条。若各端自行加减未读数，网络重连和重复事件会让差异持续扩大。改造后由云端保存最大已读位点，App 的已读操作广播给 H5 和 PC；心跳发现差异时，各端直接使用服务端结果覆盖本地缓存。

10.5 假在线与推送延迟

场景示例：手机进电梯后，服务端误以为仍在线

用户从 Wi-Fi 切到蜂窝网络时，旧 TCP 连接处于半开状态。服务端仍把新消息发往旧连接，因此没有触发 APNs/极光推送，用户直到重新打开 App 才看到消息。网关超过心跳阈值后应主动判定离线；若长连下发 3 秒没有 Client_Recv_ACK，立即转入离线推送通道。

01

动态心跳

前台约 30 秒、后台约 180 秒；需结合平台保活限制和电量实测。

02

快速断连识别

超过约 1.5 倍心跳周期未响应则关闭半开连接，切换离线状态。

03

ACK 补偿

长连下发后 3 秒未收到 Client_Recv_ACK，转离线推送；补偿消息仍需幂等。

04

推送时延

携带 push_send_time，客户端收到后计算端到端延迟并按厂商、地域、版本聚合。

Ghost Connection Ratio

> 2% 告警，检查心跳策略、NAT、网络切换和网关连接回收。

Offline Push Latency P95

> 5s 告警，按 APNs、WebPush、极光等通道拆分定位。
