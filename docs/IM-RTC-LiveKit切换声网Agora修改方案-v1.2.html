IM · RTC MIGRATION · SECURITY

IM音视频RTC：LiveKit 切换声网（Agora）方案

将 IM 音视频通话媒体面从自建 LiveKit 迁移到声网 Agora，尽量保持既有信令不变，并补齐媒体流加密、兼容迁移与安全边界。

信令层尽量不动客户端改造为主体AES-GCM2 媒体流加密双媒体层兼容迁移
文档版本v1.2
日期2026-09-29
范围sync-dm-im（信令 + Token）及客户端媒体层；不含直播业务
目标音视频通话媒体面从自建LiveKit切换为声网RTC，信令层尽量不动；支持声网内置媒体流加密；补充切换后的安全性考量

1. 背景与结论

1.1 现状：使用LiveKit媒体层

目前 IM 音视频RTC采用的是 IM 信令层 + LiveKit 媒体层 架构：

层次 职责 现有实现
信令层 邀请 / 接听 / 拒绝 / 挂断 / 忙线 / 群通话状态 / 离线推送 signal-srv + signal-job + gateway 信令通道
媒体层 进Room / 流Publish / 流Subscribe / 编解码 客户端 LiveKit SDK + LiveKit SFU 服务器
LiveKit JWT Token 用户进Room凭证 http-gateway → signal-srv.GetLivekitToken 签发 LiveKit JWT

IM 服务端与 LiveKit 的耦合点很少：只做 Token 签发，不负责 LiveKit SFU 房间生命周期管理（无服务端创建 / 销毁 LiveKit Room 的调用，token里设置了自动创建Room，SFU在房间无人 1 分钟之后自动销毁）。

1.2 目标：媒体层切换为声网服务

  • 媒体层改为声网 RTC SDK（App / PC / Web / H5 各自接入）
  • 服务端改为签发 Agora RTC Token（可复用集团内直播侧已有声网能力）
  • 支持声网内置媒体流加密（AES-GCM2，密钥由服务端生成，随 Token 下发）
  • 信令协议、通话状态机、离线推送逻辑原则上保持不变

1.3 改造体量评估

范围 体量 说明
服务端 Token + 配置 + HTTP 路由 中 新增声网 token 签发、channel 级加密 key/salt、配置项
Proto / 错误码 / 兼容期 小 建议兼容旧接口一段时间
客户端 SDK 与进房逻辑 大 改动工作量主要在客户端
信令（invite / answer / hangup） 基本不动 仅错误码文案 / 枚举可演进
运维（LiveKit 集群） 减少 改为声网控制台与用量监控，兼容器结束后可下线 LiveKit SFU

结论：后端改动可控；风险与工期主要在客户端与联调。

2. 架构变化

2.1 当前：LiveKit媒体层RTC通话交互流程

主叫/被叫客户端
    │  IM 信令（邀请/应答/挂断…）
    ▼
im-gateway / signal-srv / signal-job
    │  需要进媒体房时
    ▼
HTTP: POST /signal/v*/livekit_token
    │
    ▼
signal-srv.GetLivekitToken  ──► 签发 JWT token
    │  LiveKit JWT token
    ▼
客户端 LiveKit SDK Join(roomId, JWT token)

LiveKit JWT token 签发逻辑：

  • Grant：RoomJoin=true，Room=roomId
  • Identity：userId（字符串）
  • 有效期：tokenKeepAlive 小时

2.2 目标：声网媒体层RTC通话交互流程

主叫/被叫客户端
    │  IM 信令（不变）
    ▼
im-gateway / signal-srv / signal-job
    │
    ▼
HTTP: POST /signal/v*/agora_token
    │
    ▼
signal-srv.GetAgoraToken
    │  签发 RTC Token
    │  按 channelId 生成/复用 encryptionKey + encryptionKdfSalt（见 §4.6）
    ▼
返回：appId, agoraToken, agoraUid, encryptionMode, encryptionKey, encryptionKdfSalt
    │
    ▼
客户端：
  1) enableEncryption(mode, key, salt)   // 进房前开启媒体流加密
  2) joinChannel(appId, channelId, agoraToken, agoraUid)

2.3 两个SDK之间的概念映射

LiveKit 声网 Agora 说明
Room(房间) Channel(频道) 建议继续用现有 callId / roomId 作为 channelName
AccessToken (JWT) RTC Token 声网生成算法与 LiveKit 不同，不可混用
Identity (string) uid（uint32） 需服务器端做用户 ID 映射
ApiKey / ApiSecret App ID / App Certificate 服务器新增声网配置信息
自建 / 托管 SFU 声网云媒体服务 运维层工作变化

3. 集团已有声网直播业务

直播业务已在 sync-dm-api / sync-bi-api 使用声网 Token 与云端转码

建议：

  1. IM 侧 Token 生成抽到公共库（如 dm-common 或 im-common 下 rtc/agora），避免与直播复制多份逻辑。
  2. IM 与直播是否共用同一 Agora AppId：
    推荐 IM 独立 AppId。

注意：

直播侧曾对 userId 做低 16 位截断以适配 uid；IM 用户量更大，不可直接照搬截断策略。

4. 服务端修改方案

4.1 配置文件新增声网配置信息

signal-srv 将 livekitConf 替换，或新增加声网配置信息agoraConf：

agoraConf:
  appId: "<AGORA_APP_ID>"
  appCertificate: "<AGORA_APP_CERTIFICATE>"
  tokenExpireSec: 7200          # Token 有效期（秒），建议与权限 privilege 一致
  # 媒体流加密（内置 AES-GCM2）
  encryptionEnabled: true       # 是否默认开启媒体流加密
  encryptionMode: AES_256_GCM2  # AES_128_GCM2 | AES_256_GCM2
  cryptoTTLSec: 21600           # 同一 channel 的 key/salt 在 Redis 中的 TTL（秒），建议 ≥ 通话最长时长

4.2 UserID / 身份模型（必须先拍板）

  1. 声网进房需要uid，声网推荐的uid是 uint32 格式，与IM userId int64 格式存在冲突：
方案 做法 优点 风险
数字 user_id 映射 用映射表 im_user_id → agora_uid(uint32) 与多数原生示例一致 需处理存储和冲突；不可简单截断 int64
  1. 群通话多人同 channel：所有参与者使用同一 channelName（建议 = 现有 roomId/callId），各自不同 uid。

4.3 Token 签发 RPC

方案：新增请求声网Agora Token接口

  1. Proto 新增（Token 与加密参数一并返回，见 §4.6）：
rpc GetAgoraToken(GetAgoraTokenReq) returns (GetAgoraTokenResp);

enum AgoraEncryptionMode {
  AGORA_ENC_MODE_UNSPECIFIED   = 0;
  AGORA_ENC_MODE_AES_128_GCM2  = 1; // 推荐
  AGORA_ENC_MODE_AES_256_GCM2  = 2; // 更强，默认推荐
}

message GetAgoraTokenReq {
  string channel_id = 1;  // 对应原 roomId / callId，即声网 channelName
  string user_id    = 2;  // IM 用户 ID 字符串
  bool   enable_encryption = 3; // 可选；默认 true（与服务器配置一致时可省略）
}

message GetAgoraTokenResp {
  string channel_id = 1;
  string token      = 2;  // RTC Token
  string app_id     = 3;  // 客户端 SDK 初始化需要，建议下发避免端上写死多环境
  string agora_uid  = 4;  // 实际进房使用的声网 uid

  // —— 媒体流加密（同一 channel 内所有成员共享）——
  AgoraEncryptionMode encryption_mode = 5; // 如 AES_256_GCM2
  string encryption_key               = 6; // hex 字符串（32 字节 → 64 字符）
  string encryption_kdf_salt          = 7; // Base64(32 bytes)，客户端解码为 32 字节
}
  1. HTTP 网关服务器：
阶段 路径
新增 POST /signal/v*/agora_token
兼容 兼容期保留 /signal/v*/livekit_token

4.4 同时兼容 LiveKit 和 声网 Agora 媒体层

需要改呼叫 proto。被叫是靠收到的邀请信令选媒体层的，不能只靠客户端的本地开关控制。否则主叫已用 Agora 进房、被叫却是用 LiveKit 接听的，无法建立通话。

4.4.1 proto 消息现状

  • SIGSponsorCall / SIGSPonsorGroupCall 里没有媒体层字段；
  • 房间号实际就是 scallId / callId，
  • Token 由客户端调 HTTP 从服务器获取。

4.4.2 修改 proto 消息以同时支持 LiveKit 和 Agora

  1. 邀请信令增加 mediaProvider 区分媒体层

在 im.sig.proto 增加枚举，并写进 1v1 / 群呼的发起（及中途邀请）消息：

// 媒体层（双栈兼容期）
enum RtcMediaProvider {
  RTC_MEDIA_PROVIDER_LIVEKIT = 0; // 默认：老客户端未填时也是 LiveKit
  RTC_MEDIA_PROVIDER_AGORA   = 1;
}

message SIGSponsorCall {
  // ... 原有字段 1-8 ...
  RtcMediaProvider mediaProvider = 9; // 主叫选定的媒体层；被叫据此选 SDK / Token 接口
}

message SIGSPonsorGroupCall {
  // ... 原有字段 1-7 ...
  RtcMediaProvider mediaProvider = 8;
}

// 群通话中途邀请他人时也要带上（否则后进房的人不知道）
message SIGGroupCallJoin {
  // ... 原有字段 1-7 ...
  RtcMediaProvider mediaProvider = 8; // joinType=INVITE 时必填；APPLY 可回填当前会的 provider
}

// 应答里要带回，便于主叫确认

message SIGSponsorCallAns {
  // ... 原有 ...
  RtcMediaProvider mediaProvider = 9; // 被叫实际采用的；不支持时可拒接
}

message SIGGroupCallAns {
  // ... 原有 ...
  RtcMediaProvider mediaProvider = 7;
}
  1. HangUp、StateNotify、Finish、Busy、Disconnected一般不用改：——会话媒体层在邀请时已确定媒体层。

4.4.3 被叫怎么识别（1v1 / 群聊相同处理）

步骤 行为
1 收到 SIG_SPONSORP2PCALL_DELIVER / SIG_SPONSORGROUPCALL_DELIVER（或 JOIN 邀请）
2 读 mediaProvider：0: LiveKit(缺省)；1: Agora
3 LiveKit → 调 /livekit_token + LiveKit SDK；Agora → 调 /agora_token + Agora SDK
4 本端不支持该 provider → 拒接（Ans 失败），建议加错误码如 ERR_CALL_MEDIA_PROVIDER_UNSUPPORTED
5 呼叫方可以提示用户临时修改默认媒体层，然后再次呼叫该用户

群呼：同一次 callId 的邀请/Join 必须带相同 mediaProvider；后进房的人只认邀请里的值，不要本地再选。

4.4.4 如何决定用 LiveKit 还是 Agora？

策略 说明
主叫决定（前期兼容双媒体层阶段） 主叫端按本端能力发起呼叫时带上通话的mediaProvider，被叫端回复接听时带上支持的mediaProvider，mediaProvider不匹配就挂断并提醒用户

4.4.5 兼容原则：

  • 新字段默认 0 = LIVEKIT，老被叫忽略未知字段，继续走 LiveKit（仅当主叫也仍是 LiveKit 时安全）。
  • 老被叫回复的Ans信令里面没有 mediaProvider 字段。在用新客户端呼叫老客户端进行 1v1 通话时，可以默认老程序回复的 mediaProvider 字段为默认值 LiveKit。现有接听逻辑要加上根据对方应答的 mediaProvider 字段判断是否应该继续通话。如果呼叫时用的是 Agora，但是发现对方回复的 mediaProvider 不是 Agora，客户端的处理流程待讨论。是挂断后以 LiveKit 重新呼叫，还是如何？

4.5 明确不改动部分

  • SignalMsg 邀请应答挂断状态机
  • signal-job 在线转发 / 离线推送
  • Mongo 信令落库、群通话消息拉取
  • callId / 群 roomId 生成规则（可原样作为 channelName）

4.6 声网媒体流加密（内置 AES-GCM2）

声网 RTC 支持对音视频媒体流加密，保证传输过程中仅持有正确密钥的频道成员可正常收听/收看。官方文档：Media Stream Encryption。

4.6.1 能力选型

类型 说明 本期建议
内置媒体流加密 SDK enableEncryption，算法为 AES-GCM2，密钥由业务服务器生成并下发 采用
自定义加密 registerPacketObserver，App 自研加解密算法 本期不做；仅当合规强制自研算法时再评估

内置加密即可满足「密钥自管、传输加密」需求；与 LiveKit 侧 E2EE 不是同一套协议，双栈期两套密钥体系互不混用。

4.6.2 encryptionKey / encryptionKdfSalt 格式

参数 格式 推荐生成方式 客户端用法
encryptionKey 字符串；建议 32 字节随机数的 hex（64 个十六进制字符） openssl rand -hex 32 或 crypto/rand + hex 赋给 EncryptionConfig.encryptionKey（Web 端按 SDK 要求做 hex→ASCII）
encryptionKdfSalt 正好 32 字节；传输用 Base64 字符串 openssl rand -base64 32 Base64 解码为 byte[32] / Uint8Array(32) 再赋给 encryptionKdfSalt
encryptionMode 枚举 配置默认 AES_256_GCM2 与 key/salt 一并传给 SDK

Go 服务端生成示例：

func genEncryptionKey() (string, error) {
    b := make([]byte, 32)
    if _, err := rand.Read(b); err != nil {
        return "", err
    }
    return hex.EncodeToString(b), nil // 64 字符 hex
}

func genEncryptionKdfSaltBase64() (string, error) {
    b := make([]byte, 32)
    if _, err := rand.Read(b); err != nil {
        return "", err
    }
    return base64.StdEncoding.EncodeToString(b), nil
}

4.6.3 一通一密，同房共享

范围 要求
同一通通话 / 同一 channel 所有成员必须使用同一套 mode + key + salt，否则黑屏 / 无声
不同通话 每次通话重新生成 key 与 salt（官方安全建议）

不要使用全局固定密钥，也不要给每个用户发不同密钥。

4.6.4 与 Token 接口一并下发（推荐）

客户端取 Token 时同时拿到加密参数，进房流程为：

POST /signal/v*/agora_token
  → 返回 token + appId + uid + encryption_mode + encryption_key + encryption_kdf_salt
  → enableEncryption(...)
  → joinChannel(...)

服务端按 channelId（callId） 保证同房参数一致：

GetAgoraToken(channel_id, user_id)
  1. 鉴权：当前用户是否有权加入该通话（建议校验 call 成员）
  2. 查 Redis：im:agora_crypto:{channel_id}
  3. 不存在 → 生成 key/salt，写入 Redis，TTL = cryptoTTLSec
  4. 存在 → 直接读取
  5. 签发该用户 RTC Token，与加密字段一并返回

Redis 建议结构（JSON）：

{
  "mode": 2,
  "key": "<64-hex>",
  "salt": "<base64-32bytes>",
  "created_at": 1710000000000
}

挂断 / 会议结束后可主动 DEL im:agora_crypto:{channel_id}；即使未删，TTL 到期自动失效。

4.6.5 服务端实现要点（signal-srv）

  1. 在 GetAgoraToken 中集成 key/salt 生成与 Redis 共享逻辑。
  2. 配置项见 §4.1 encryptionEnabled / encryptionMode / cryptoTTLSec。
  3. encryptionEnabled=false 时，响应中加密字段可留空，客户端跳过 enableEncryption。
  4. 日志禁止打印完整 key/salt/token；可打 channel_id、mode、是否命中 Redis。
  5. 公共库可抽到 im-common/rtc/agora：BuildRtcToken + GetOrCreateChannelCrypto。

4.6.6 客户端实现要点

  1. 必须先 enableEncryption，再 joinChannel。
  2. 同一通话所有端使用响应里同一套 mode/key/salt；本地不得改写。
  3. Salt：Base64Decode(encryption_kdf_salt)，长度必须为 32。
  4. 若加密字段为空且配置要求加密 → 视为错误，不要进房。
  5. Web：按 Agora Web SDK 文档处理 key（hex→ASCII）与 salt（Base64→Uint8Array）。
  6. 注意：声网不支持将已开启媒体流加密的流直接旁路推 CDN（IM 通话一般无此需求）。

Android 示意：

EncryptionConfig config = new EncryptionConfig();
config.encryptionMode = EncryptionConfig.EncryptionMode.AES_256_GCM2;
config.encryptionKey = resp.getEncryptionKey();
config.encryptionKdfSalt = Base64.decode(resp.getEncryptionKdfSalt(), Base64.DEFAULT);
rtcEngine.enableEncryption(true, config);
rtcEngine.joinChannel(token, channelId, null, agoraUid);

4.6.7 与双媒体层兼容的关系

mediaProvider 加密策略
LiveKit 不走本节；沿用 LiveKit 既有加密 / E2EE（如有）
Agora 走本节内置加密；从 agora_token 响应取 key/salt

mediaProvider 仍只负责选 SDK；加密材料不放在邀请信令里，统一由 Token 接口下发，避免信令落库扩大密钥暴露面。

4.6.8 自定义加密（后续可选，本期不做）

若合规要求自研算法，可使用 registerPacketObserver，在收发音频/视频包回调中加解密。需全端（含 Web）能力评估与压测，实现与维护成本明显高于内置加密。

加密能解决「媒体内容是否可被第三方听懂/看懂」；切换云媒体后还有元数据、IP、密钥托管边界等问题，详见 §7 安全性考量。

5. 客户端修改方案（工作量主体）

5.1 各端任务

端 任务
iOS / Android App 去掉 LiveKit SDK，接入 Agora RTC SDK；进房参数改为 appId / channel / token / agora_uid
Windows / macOS PC 同上
Web / H5 / Hybrid agora-rtc-sdk-ng（或现网选用版本）；注意浏览器权限与自建域名
Telegram 内嵌 H5 单独验证 WebView 权限与自动播放策略

5.2 通话流程对齐（信令除呼叫邀请信令增加mediaProvider之外不变）

  1. 信令协商成功（或主叫发起后）→ 请求 agora_token（响应含 Token + 加密参数）。
  2. 先 enableEncryption(mode, key, salt)，再 joinChannel（对应原 LiveKit connect / joinRoom）。
  3. 挂断信令发出后 → leaveChannel + 释放设备。
  4. 被叫拒绝 / Token失败 / 加密参数缺失 / 连接失败 → 继续上报现有或新增 errCode。

5.3 能力对照清单（联调用）

  • 1v1 语音 / 视频
  • 群通话多人音视频
  • 切换摄像头、静音、免提
  • 通话中断（杀进程、弱网、切换前后台）
  • 忙线、超时未接
  • 与推送唤醒进房的时序（先信令还是先 Token）
  • 媒体流加密：双方/多方开启加密后音视频正常；故意使用错误 key 应无法互通

5.4 UI / 产品

  • 设置页提供RTC媒体层选择控制项，让用户选择「基于LiveKit」还是「基于声网」。
  • 质量监控若有上报 LiveKit stats，根据上述控制项选择是上报LiveKit埋点还是上报声网埋点。

6. 分阶段落地计划

Phase 0：准备（约 1 周）

  • 申请 IM 专用 Agora 项目（AppId/证书），划定区域与套餐。
  • 拍板 uid 映射方案。
  • 声网channel 命名规范：im_{callId} 或沿用现 roomId（文档冻结）。
  • 确认与直播 AppId 隔离策略。

Phase 1：服务端（约 2 周）

  • im-common proto + 生成代码（含 GetAgoraToken 加密字段）
  • signal-srv Agora Token 签发
  • channel 级 encryptionKey / salt 生成与 Redis 共享
  • http-gateway 新路由
  • 配置与密钥注入（含 encryptionEnabled / encryptionMode / cryptoTTLSec）
  • 单测：Token 校验；同 channel 两次取 Token 返回相同 key/salt；不同 channel 不同

Phase 2：客户端开发（约 3 周）

  • 特性开关：rtc_provider=livekit | agora
  • 内部 LiveKit / Agora 媒体层切换
  • Agora 进房前 enableEncryption 对接
  • 打通 1v1 通话（含加密）
  • 打通群通话（含加密，多人同 key）

Phase 3：全量与收尾

  • 全量切 Agora
  • 下线 LiveKit Token 接口与依赖
  • 下线 LiveKit 服务与监控
  • 文档与错误码注释清理

回滚策略

  • 服务端保留兼容双媒体层一个版本周期。
  • 客户端未升级用户仍走 LiveKit（若双媒体层）；一旦 LiveKit 下线，必须强制升级客户端。

7. 安全性考量

切换到声网后，媒体面由「自建 / 托管 LiveKit SFU」变为「声网云 SD-RTN」。本节从能否听内容、IP 是否泄露、元数据暴露、密钥边界等角度说明风险与对策，并与现状 LiveKit 对比。

7.1 威胁模型（先界定「谁」）

角色 可能接触什么
通话双方客户端 明文音视频（本地采集/播放）、Token、encryptionKey/salt
我方 IM 服务端 信令内容、callId、Token 签发、crypto key/salt（Redis）
声网云（媒体中继） 媒体传输路径上的报文、连接侧 IP、channel/uid 等元数据
网络中间人（运营商/Wi‑Fi） 传输中的数据包（若未加密则为可解析媒体；加密后多为密文）
对端用户 / 恶意第三方 试图猜测 channel、盗用 Token、探测对端公网 IP

结论：在强制开启内置媒体流加密（§4.6）且密钥仅由我方服务器生成并只下发给合法成员的前提下——

  • 声网不能「听到和看到」通话内容的明文数据（其转发的是密文媒体包，没有 business key/salt）。
  • 通话对端不会因为走声网而直接拿到你的公网 IP（标准频道模式为客户端 ↔ 声网边缘节点，而非端到端打洞直连）。
  • 声网作为云厂商仍能看到连接元数据（含客户端出口 IP、channel、uid、时长等），这与任何 SaaS 媒体服务同类；需用合同、区域与配置约束。

7.2 声网能否监听通话内容？

7.2.1 未开启媒体流加密时

客户端音视频在到达声网边缘后，媒体面由声网 SFU/转发网络处理。此时：

  • 理论上云侧具备接触未加密媒体载荷的技术可能（与自建 LiveKit 未启用 E2EE 加密时，运维可接触明文媒体类似）。
  • 因此：切换声网但是不对音视频数据加密时，和自建 LiveKit 安全性是一样的；只是信任边界从「机房运维」换成「声网 + 合同/合规」。

7.2.2 启用声网内置加密后

音视频数据的处理流程：

采集 → SDK 用我方 key/salt 加密 → 密文包经声网转发 → 对端用同一 key/salt 解密 → 播放
问题 结论 原因
声网能否听到 / 看到内容的明文数据？ 正常情况下不能 key/salt 由我方 signal-srv 生成，只经我方 HTTPS Token 接口发给成员；声网签发/校验的是 RTC Token（进房凭证），不需要、也不应持有媒体加密 key
声网能否「加入频道监听」？ 无业务 key，无法解密加密数据的媒体数据 即使其员工或系统进同 channel，没有 encryptionKey/salt 也只能拿到密文流

7.2.3 仍可能导致「内容可被第三方听到」的例外（必须规避）

场景 风险 对策
未启用 enableEncryption 云侧 / 链路都可能接触明文媒体 配置 encryptionEnabled=true，客户端强制先加密再进房
云端录制 / 旁路推流 / 旁路转码 部分能力要求明文或厂商侧处理 IM 通话默认关闭录制与 CDN 旁路；文档已说明加密流不支持直接推 CDN
key/salt 泄露（日志、抓包 HTTP、Redis 未鉴权） 持有密钥者可解密 HTTPS、日志脱敏、Redis ACL、一通一密、结束删 key、Token 接口鉴权
错误把 key 放进邀请信令并落库 扩大暴露面 加密材料只走 agora_token，不进 SIG* 信令（§4.6.7）
App Certificate 泄露 攻击者可伪造进房 Token 证书仅存服务端；轮换；channel 用不可猜 callId

相对 LiveKit 自建：自建 SFU 时运维若未做媒体加密，同样可接触明文。本期用「业务侧托管密钥 + 声网只转发密文」，在内容保密相对云厂商这一点上，通常优于「上云但不加密」，与「自建 + 同等强度加密」同级，信任根在我方密钥系统。

7.3 IP 是否会泄露？为什么不会（或会）？

需区分「泄露给谁」。

7.3.1 会不会泄露给通话对端（另一方用户）？

模式 对端能否看到你的公网 IP
纯 P2P / 主机 ICE 直连 容易通过 Candidate 暴露公网/局域网 IP
声网标准 RTC 频道 一般不会

原因：

  1. 媒体路径是 客户端 ↔ 声网边缘节点 ↔ 对端客户端，不是 Mutual 直连。
  2. SDK 默认走声网 SD-RTN / 中继，对端看到的是声网节点地址，而不是你的家庭/公司出口 IP。
  3. 与当前 LiveKit SFU（客户端进你们或托管的 SFU，再转发）模型同类：对端 IP 互不可见是 SFU 架构的常态。

因此：「换声网会导致对方拿到我的 IP」——在标准进房模型下是不成立的。

7.3.2 会不会泄露给声网？

连接声网必须的连接信息会。 客户端连声网边缘时，声网必然看到：

  • 客户端出口公网 IP、大致地理/运营商信息
  • 连接时间、时长、channelId、agora_uid、质量统计（若开启）

这与使用任何云通讯、对象存储、CDN 相同，属于对云厂商的元数据暴露，不是「对端用户泄露」。

对策：

  • 合同与 DPA：数据处理、留存周期、分包。
  • 选择合规区域 / 专网入口（若商务提供）。
  • channel 命名避免携带手机号、真实姓名等（用 UUID callId）。
  • 关闭不必要的客户端详细质量上报到第三方。

7.3.3 会不会泄露给我方服务端 / 其他用户？

路径 是否暴露客户端 IP
拉取 agora_token（http-gateway） 我方网关可见客户端 IP（与现网拉 livekit_token 相同）
IM 信令链路 我方可见（与现网相同）
仅因「对端也在同一 Agora channel」 不会因此获得你的 IP

7.3.4 与 LiveKit 对比（是否会泄露IP）

项 自建 LiveKit SFU 声网云
对端是否看到你的 IP 通常否（SFU） 通常否（云 SFU/中继）
谁看到你的连接 IP 机房 / 托管商 声网
信任边界 自建运维 云厂商 + 合同

切换声网不会额外增加「对端 IP 泄露」的风险；变化的是连接 IP 的可见方从自建服务器变成了声网。

7.4 元数据与隐私（即使内容已加密）

即使媒体内容加密，下列信息仍可能被声网或链路观察到：

元数据 说明 缓解
channelName 若用可预测 ID，可能被撞库进房 使用高熵 callId；Token 绑定 uid+channel+过期时间
agora_uid 可关联多次通话 映射表权限收紧；勿把 IM 手机号当 uid
通话起止时间、时长 行为画像 合同约束；业务侧最小化日志
AppId 项目标识 IM 独立 AppId，与直播隔离

信令（邀请文案、好友关系等）仍只走我方 IM，不经过声网；声网不知道聊天文本，只知道「某 uid 进了某 channel」。

7.5 Token、密钥与接口安全基线

项 要求
传输 agora_token 必须 HTTPS；禁止明文 HTTP
鉴权 仅登录用户可调；校验 user_id 与 Token 主体一致；建议校验其为该 callId 成员
App Certificate 仅存服务端配置中心；不进客户端、不进仓库
encryptionKey/salt 一通一密；Redis ACL；日志脱敏；通话结束 DEL 或短 TTL
RTC Token 短过期（如 1～2 小时）；权限最小化（仅当前 channel）
防重放 / 刷接口 网关限流；异常 channel 请求告警

7.6 安全结论

  1. 内容窃听（声网）：在默认开启 §4.6 内置加密、密钥我方托管的前提下，声网无法解密通话内容；未加密时则与「未加密自建 SFU」无差别，不推荐。
  2. IP 泄露给对端：标准声网频道模式不会把客户端公网 IP 暴露给对端；机制与 SFU 相同。
  3. IP 暴露给声网：会（连其边缘节点的必要信息）；需合同与区域策略接受或约束。
  4. 相对现状 LiveKit：对端 IP 风险改变不大；内容保密行取决于是否启用了数据加密；主要变化是从使用自己设置的SFU云变成了信任云厂商处理元数据与可用性，应用声网的加密算法提升安全性。

8. 运维、质量与合规

项 LiveKit 现状 声网切换后
SFU 部署 需维护 / 托管 无需自建媒体服务器
监控 sync-bi-api 等 livekit_* 指标 改用声网控制台 + 自建上报（可选 Agora Analytics）
合规 自建机房数据路径 确认声网区域与数据驻留要求；参见 §7
成本 机器 + 带宽 按分钟计费，需用量预估
内容保密 依赖是否自建侧加密 依赖 §4.6 媒体流加密 + 我方密钥托管

sync-bi-api 中 livekit_* Prometheus 指标与 audio_video_log.server_ip 等字段需评估改为「RTC 厂商中立」字段或声网侧字段，避免报表空洞。

9. 风险与对策

风险 对策

10. 验收标准

  1. 1v1 音视频：接通、挂断、拒接、超时、忙线与现网一致。
  2. 群通话：多人进房、中途加入/退出、结束会议信令正常。
  3. App / PC / Web（H5）均走声网进房成功。
  4. Token 接口鉴权有效，过期后无法进房。
  5. 开启媒体流加密后，同房成员音视频正常；错误 key/salt 无法互通。
  6. 同一 callId 多次取 Token，encryption_key / salt 一致；不同 callId 不一致。
  7. 安全抽检：日志无完整 token/key/salt；agora_token 接口未登录不可访问；加密强制开启时客户端未加密不能进房。
  8. 无关模块无回归问题。
